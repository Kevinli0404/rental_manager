# 架構決策紀錄

每個重要決定記一筆：決定了什麼、為什麼、沒採用哪些做法。新的決策加在最後面，舊的不刪；推翻時新增一筆，並在舊的那筆註明被哪一筆取代。

格式：

```
## D-000 標題
- 日期：
- 決定：
- 原因：
- 沒採用的做法：
- 影響：
```

## D-001 本機優先，第一版不接後端
- 日期：2026-11-04
- 決定：第一版只用 drift 把資料存在裝置上，不登入、不同步。
- 原因：點交現場常常沒有網路。先把離線填寫、簽名、PDF 做完整，比一開始就處理同步更快做出能用的東西。
- 沒採用的做法：一開始就接雲端後端。
- 影響：資料結構要先為同步做準備（見 D-003）。

## D-002 第二階段的後端用 Supabase
- 日期：2026-11-04
- 決定：要做雲端同步時用 Supabase（PostgreSQL、Auth、Storage、Row Level Security）。
- 原因：資料表可以跟本機的 drift 一一對應；同步邏輯自己寫，能展示離線同步的設計；Row Level Security 可以做到每個人只看得到自己的資料。
- 沒採用的做法：
  - Firebase Firestore：內建離線快取很方便，但同步幾乎都由它處理，看不出自己的設計。
  - 自己架伺服器：主機、更新、資安、HTTPS 憑證都要自己顧，會佔掉大部分時間。
- 影響：免費專案一段時間沒使用會暫停，展示前要確認專案有在運作。

## D-003 主鍵用 UUID，每張表有 updatedAt 和 deletedAt
- 日期：2026-11-04
- 決定：所有表的主鍵用 UUID 字串；每張表都有 `updatedAt`；刪除一律軟刪除（`deletedAt`）。
- 原因：之後多台裝置同步時，UUID 不會撞號；`updatedAt` 用來判斷哪邊比較新；軟刪除才能把「刪除」這件事也同步出去。
- 沒採用的做法：自動遞增的數字主鍵、直接刪除資料列。
- 影響：所有查詢都要排除已刪除的資料。

## D-004 建立點交時存一份空間配置快照
- 日期：2026-11-04
- 決定：建立點交紀錄時，把範本（或入住紀錄）的空間和項目整份複製，存進該筆紀錄的 `layoutJson`；草稿期間可以在這份配置上新增、複製、刪除空間。
- 原因：點交單是雙方簽過名的紀錄，之後範本改版不能讓舊紀錄跟著改變；而且每間房子的空間數量不同，例如兩間臥室。
- 沒採用的做法：只存範本 ID 和版本號（這樣就得永遠保留每一版範本，也沒辦法增減空間）。
- 影響：紀錄會比較大，但每筆都能獨立顯示和產生 PDF；退租可以直接沿用入住的配置來對照（見 D-010）。

## D-005 照片和簽名只存相對路徑
- 日期：2026-11-04
- 決定：照片、簽名存成檔案，資料庫只記錄相對於 Documents 目錄的路徑。
- 原因：iOS 更新 App 之後，沙盒的絕對路徑可能會改變，存絕對路徑會找不到檔案。
- 沒採用的做法：存絕對路徑；把圖片直接存進資料庫。
- 影響：讀檔時要由 file_store 組出完整路徑。

## D-006 點交頁依狀態切換唯讀，不拆成兩頁
- 日期：2026-11-04
- 決定：草稿和已簽名共用同一個點交頁，依狀態決定能不能編輯。
- 原因：編輯頁和檢視頁分開維護，內容很容易越改越不一致。
- 沒採用的做法：另外做一個檢視頁。
- 影響：每個可編輯的元件都要支援唯讀狀態。

## D-007 填寫時自動儲存，不設儲存按鈕
- 日期：2026-11-04
- 決定：每次變更都立即寫入資料庫。
- 原因：在現場使用時，App 隨時可能被切走或關掉，自動儲存才不會掉資料，離開頁面也不用問要不要存。
- 沒採用的做法：統一按「儲存」寫入。
- 影響：寫入要夠快；連續輸入的文字欄位（例如備註）要做防抖。

## D-008 enum 存成文字
- 日期：2026-11-04
- 決定：資料庫裡的 enum 一律存名稱文字（drift 的 `textEnum`）。
- 原因：存 index 的話，enum 一調整順序，舊資料的意思就錯了。
- 沒採用的做法：存 index（intEnum）。
- 影響：enum 的名稱改了，要寫 migration。

## D-009 主要裝置是手機
- 日期：2026-11-04
- 決定：版面以手機直式為主；平板能正常操作就好。
- 原因：點交時要在屋內邊走邊檢查、拍照，手機最方便。
- 沒採用的做法：平板左右分欄的版面。
- 影響：點交頁用空間分頁，一次只顯示一個空間的項目。

## D-010 退租對照入住放進第一版（精簡版）
- 日期：2026-11-04
- 決定：退租點交沿用最近一次已簽名入住的空間配置，逐項顯示入住時的狀況，標出變差的項目；PDF 列出差異。
- 原因：點交最主要的用途，就是退租時對照入住、釐清損壞責任；沒有對照，入住和退租只是兩份互不相關的表單。沿用空間配置後 key 都一致，實作成本不高。
- 沒採用的做法：
  - 留到第二版：少了這個，第一版就缺最核心的價值。
  - 用空間名稱比對：名稱可能被改，不可靠。
- 影響：沿用自入住的空間在退租時不能刪除；被對照的入住紀錄不能刪除；押金計算和照片並排比對不在第一版。

## D-011 新增的空間用 UUID 當 key
- 日期：2026-11-04
- 決定：由範本產生的空間沿用範本的 key；之後新增、複製的空間用新的 UUID，用過的 key 不再使用。
- 原因：如果用「bedroom-2」這種流水號，刪掉再新增會拿到同一個 key，可能對到已刪除的舊資料。
- 沒採用的做法：依空間類型編流水號當 key。
- 影響：畫面上的「臥室 2」只是顯示名稱，跟 key 無關。

## D-012 lint 用 flutter_lints 再加嚴
- 日期：2026-11-04
- 決定：以 `flutter create` 內建的 flutter_lints 為基礎，在 `analysis_options.yaml` 打開 `strict-casts`、`strict-inference`、`strict-raw-types`，另外加上非同步、型別、錯誤處理相關的規則（例如 `unawaited_futures`、`avoid_dynamic_calls`、`only_throw_errors`）。
- 原因：不用新增套件，每一條加上去的規則都寫得出理由；自動儲存和資料庫 watch 會大量用到 Future、Stream，漏 await 或忘了取消訂閱都很難查，要靠 lint 先擋。
- 沒採用的做法：very_good_analysis（規則更完整，但要多一個套件，規則數量多，之後產生檔和測試可能要另外排除）。
- 影響：`fvm flutter analyze` 要維持 0 issue；之後加入 build_runner 時，要評估產生檔是否從分析中排除。

## D-013 build_runner 產生的檔案一起 commit
- 日期：2026-11-04
- 決定：`*.g.dart`、`*.freezed.dart` 這類產生檔跟著原始碼一起 commit，不加進 `.gitignore`。
- 原因：clone 下來或 CI 不用先跑 build_runner 就能 analyze 和測試；review 時看得到產生結果的變化。`CLAUDE.md` 的完成定義也要求改了來源就要重跑 build_runner。
- 沒採用的做法：產生檔不進版控，CI 和每個人自己跑 build_runner。
- 影響：改了來源卻忘了重跑，產生檔會跟來源不一致；之後如果發生，再考慮在 CI 加檢查。

## D-014 時間存成 ISO-8601 文字
- 日期：2026-11-04
- 決定：drift 開啟 `store_date_time_values_as_text`，`createdAt`、`updatedAt`、`deletedAt`、`signedAt` 在資料庫裡存成 ISO-8601 文字（例如 `2026-11-04T03:20:05.123Z`）。
- 原因：drift 預設存 Unix 時間（整數秒），會丟掉毫秒；存文字保留毫秒和 UTC 標記，直接看資料庫也看得懂。第二階段和 Supabase 同步時，用 `updatedAt` 判斷哪邊比較新，精度越高越好。
- 沒採用的做法：drift 預設的整數秒。
- 影響：這個設定改了要寫 migration 轉換舊資料，所以一開始就決定。

## D-015 drift 產生的 schema 測試輔助檔不做靜態分析
- 日期：2026-11-04
- 決定：`analysis_options.yaml` 排除 `test/drift/*/generated/**`。
- 原因：這些檔案由 `drift_dev` 產生、不能手改；檔頭已經關掉 lint，但 `strict-raw-types` 是分析器的語言檢查，檔頭關不掉。其他產生檔（`*.g.dart`、`*.freezed.dart`）在目前的規則下沒有問題，照常分析（延續 D-012 的評估）。
- 沒採用的做法：關掉整個專案的 `strict-raw-types`；手改產生檔（下次產生就被蓋掉）。
- 影響：只排除這一個資料夾，自己寫的程式碼和測試仍然完整檢查。

## D-016 repository 只在需要時才加
- 日期：2026-11-04
- 決定：provider 可以直接呼叫 DAO。只有要處理檔案（照片、簽名），或商業規則要組合好幾個 DAO 時，才加 repository。刪除物件時連帶刪除點交紀錄，用 DAO 裡的交易處理。
- 原因：T2 的物件只有新增、修改、讀取和刪除，加一層 repository 幾乎都是轉呼叫 DAO，徒增檔案和測試。drift 的 DAO 本身就能宣告多張表並開交易。
- 沒採用的做法：照原本的分層，provider 一律透過 repository。
- 影響：`architecture.md` 的分層改成「repository 需要時才加」。之後加 repository 時，同一個功能的寫入都改走 repository，不要一半走 DAO、一半走 repository。

## D-017 provider 手寫，不用 riverpod codegen
- 日期：2026-11-05
- 決定：用 flutter_riverpod 3 手寫 provider（`Provider`、`StreamNotifierProvider` 等），不加 riverpod_annotation、riverpod_generator。
- 原因：riverpod_generator 最新版（4.0.9）要求 `build` <5，專案的 build_runner 2.17.1 需要 build 5.0.x，兩者裝不在一起；要用 codegen 就得把 build_runner 降版，它還會帶進 prerelease 的 riverpod_analyzer_utils（1.0.0-dev.12）。目前 provider 很少，手寫只多幾行型別宣告。
- 沒採用的做法：降版 build_runner 來配合 riverpod_generator。
- 影響：`architecture.md` 的技術選擇改成手寫 provider。riverpod_generator 支援 build 5 之後可以再評估；要換就一次全部換，不要手寫和 codegen 混用。

## D-018 刪除目前頁面的資料時，等頁面退場後才寫入
- 日期：2026-11-05
- 決定：在詳情頁刪除自己顯示的資料（例如物件）時，先 `context.go` 回上一層，等這頁的退場動畫結束（`ModalRoute.completed`）才寫入資料庫。刪除失敗時用事先取出的 `ScaffoldMessenger` 在上一層顯示錯誤。
- 原因：畫面用 watch 查詢，資料一改就重畫；退場動畫中的頁面還在畫面上，也會跟著重畫。先刪除再離開，或離開後馬上刪除，退場動畫（iOS 是 0.5 秒）中都會閃過「找不到這個物件」。widget test 逐格檢查過這個情況。
- 沒採用的做法：詳情頁記住最後一次讀到的資料，查詢變成 null 時繼續顯示舊資料（每個查詢都要各自處理，T3 加上點交紀錄列表後也會一起變空）；接受閃一下。
- 影響：刪除會晚一個退場動畫的時間才寫入；這段時間關掉 App 的話不會刪除。T3 刪除點交紀錄時照同樣的做法。

## D-019 App 只用繁體中文，不跟著裝置語系切換
- 日期：2026-11-10
- 決定：加入 flutter_localizations（Flutter SDK 內建），`MaterialApp` 的 `locale` 和 `supportedLocales` 都只有 zh_TW。日期選擇器、返回按鈕這些 Material 內建文字都用繁體中文，裝置設成其他語系也一樣。
- 原因：T3 新增點交要用 `showDatePicker`，沒有設定語系時，月份、星期和按鈕都是英文。App 自己的文字只有繁體中文，跟著裝置切換的話，畫面會中英混雜。
- 沒採用的做法：不設定語系（內建文字維持英文）；`supportedLocales` 加上英文、跟著裝置切換（App 自己的文字沒有英文版）。
- 影響：之後要支援其他語言時，App 自己的文字要先改用 gen-l10n，再加 `supportedLocales`。

## D-020 刪除空間時，項目結果和照片一起軟刪除
- 日期：2026-11-12
- 決定：刪除空間時，在同一個交易裡把空間從空間配置拿掉，並把這個空間的項目結果和照片軟刪除。之前已經刪掉的保留原本的刪除時間。
- 原因：空間 key 不會再用（D-011），留下來的結果和照片不屬於任何空間，畫面和 PDF 都不會顯示，但第二階段同步時會被上傳。一起標記刪除，資料庫裡才不會累積這些資料。
- 沒採用的做法：只從空間配置拿掉，結果和照片留在資料庫（跟刪除點交紀錄時不逐筆標記一樣，程式比較少）。
- 影響：照片檔案本身的清理在 T4 處理。刪除點交紀錄、物件時仍然不逐筆標記底下的資料。

## D-021 照片用 image_picker 內建的縮小功能，保留它輸出的格式
- 日期：2026-11-12
- 決定：拍照、選相簿用 image_picker，縮小和壓縮也用它的 `maxWidth`、`maxHeight`、`imageQuality`（長邊 1600、品質 80），不另外加圖片處理套件。存檔時副檔名照實際格式：通常是 `photos/{inspectionId}/{photoId}.jpg`，相簿裡的 PNG、GIF 是 `.png`、`.gif`。
- 原因：查過 image_picker iOS 版的原始碼，相機拍的照片、相簿裡的 HEIC 和 JPEG 都會輸出成 JPEG，並縮小、壓縮；只有 PNG、GIF 保留原格式，只縮小不壓縮。這兩種在點交照片裡很少見，為了它們加套件、寫轉檔不划算。
- 沒採用的做法：再用 image 套件把 PNG、GIF 轉成 JPEG（多一段轉檔程式和測試）；用 flutter_image_compress 統一轉檔（它的縮小參數是最小寬高，要自己算比例，而且只有這裡用到）。
- 影響：PNG 截圖的檔案比較大；T7 產生 PDF 時要確認 JPEG 以外的格式也能放進去。Android 版的輸出格式還沒查原始碼確認。
